## 1. 프로젝트 개요 (한눈에 보기)

### 프로젝트 목적
‘플라워샵 근무 관리’는 여러 플라워샵의 직원 가입, 출퇴근 기록, 급여 계산을 관리하는 웹 프로그램입니다. 급여 방식은 **시급** 또는 **월급** 중 하나이며, 급여 방식과 금액은 적용 시작일을 기준으로 계산합니다.

### 역할
1. **시스템 관리자**: 플라워샵을 등록하고 이름을 수정합니다.
2. **플라워샵 관리자**: 본인 플라워샵의 직원 가입을 승인하고, 직원 상태·급여 조건·근무 기록·월별 정산을 관리하며, 로그인 화면에서 본인 정보(이름, 비밀)를 직접 수정할 수 있습니다.
3. **플라워샵 직원**: 가입을 신청하고, 승인되어 재직 중일 때 본인의 근무 기록과 급여 내역을 조회·관리합니다. (직원 로그인 대상에서 대표 관리자는 완전히 제외됩니다.)

### 핵심 동작 규칙 및 42501(RLS 정책 위반) 에러 해결 가이드
- **원인**: Supabase 테이블에 `USING (false)` RLS(행 수준 보안) 정책이 걸려 있는 상태에서 브라우저(클라이언트 컴포넌트)가 직접 `INSERT`/`UPDATE`/`DELETE`를 수행하면 `42501` 에러가 발생합니다.
- **해결 규칙**: 시스템 관리자 등록, 플라워샵 등록, 관리자/직원 로그인 및 가입, 모든 데이터 수정 작업은 **반드시 Next.js Server Actions 또는 API Route에서 `SUPABASE_SERVICE_ROLE_KEY`를 사용하는 전용 서버 클라이언트(`lib/supabase-server.ts`)**를 통해 처리해야 합니다. 브라우저 클라이언트(`createClient` with anon key)는 오직 데이터 읽기(`SELECT`) 또는 서버 액션 호출 용도로만 사용해야 합니다.
- 모든 테이블이 삭제된 경우 `supabase/migrations/0001_initial_schema.sql` 스크립트를 Supabase SQL Editor에 다시 실행하여 테이블을 재생성합니다.
- 모든 화면 상단에 ‘플라워샵 근무 관리’ 프로그램 배너를 구성하고 현대적이고 세련된 카드 레이아웃을 적용합니다.
- 인증 및 보안 관련 입력 라벨은 ‘비밀’, ‘비밀 확인’으로 표시합니다.
- 메인 화면 상단 배너 바로 아래에 ‘플라워샵 관리’ 버튼을 배치하고, 하단에 별도 영역으로 지정된 플라워샵 목록에서 ‘선택’ 버튼을 눌러 해당 플라워샵으로 이동합니다.
- 시스템 관리자가 없으면 `/system-setup`에서 최초 계정을 만들고, 계정이 이미 있으면 해당 화면에서 로그인합니다.

## 2. 사용자와 사용 시나리오

### 사용자 역할 및 권한

| 역할 | 인증 | 허용되는 작업 |
| --- | --- | --- |
| 시스템 관리자 | 이름 + 숫자 4자리 ‘비밀’ | 전체 플라워샵 조회, 등록, 이름 수정 |
| 플라워샵 관리자 | 플라워샵 선택 + 관리자 이름 + 숫자 4자리 ‘비밀’ | 소속 플라워샵 직원 신청 승인, 재직·퇴사 상태 변경, 급여 유형·금액·적용 시작일 관리, 소속 직원 근무 기록 보완, 월별 정산 조회, **로그인 화면에서 본인 정보(이름, 비밀) 수정** |
| 플라워샵 직원 | 플라워샵 선택 + 본인 이름 + 숫자 4자리 ‘비밀’ | 가입 신청, 재직 상태일 때 본인 출퇴근 기록 추가·수정, 본인 월별 근무·급여 조회, 본인 ‘비밀’ 변경 *(대표 관리자는 직원 로그인 대상에서 완전히 제외)* |

### 사용 흐름
1. 시스템 관리자가 없는 첫 방문은 시스템 관리자 최초 등록 화면으로 안내합니다.
2. 시스템 관리자는 메인 화면의 ‘플라워샵 관리’에서 인증한 뒤 플라워샵을 등록하거나 이름을 수정합니다.
3. 사용자가 메인 화면에서 플라워샵을 ‘선택’합니다. 해당 플라워샵에 관리자가 없으면 관리자 등록을 시작할 수 있고, 관리자가 있으면 관리자 로그인(본인 정보 수정 포함)과 직원 기능을 사용할 수 있습니다.
4. 직원은 플라워샵별 가입 신청을 합니다. 관리자는 신청자를 승인하면서 급여 유형, 금액, 적용 시작일을 설정합니다. 승인 이후 직원 상태는 재직이 됩니다.
5. 시급 직원은 날짜별 출근·퇴근 시각을 등록합니다. 월급 직원은 출퇴근을 입력하지 않습니다. 관리자는 직원별 상세 내역과 월별 지급액을 확인하고 필요하면 근무 기록을 보완합니다.
6. 퇴사 처리된 직원 및 대표 관리자는 직원 로그인 선택 목록에서 제외되고, 과거 기록과 정산 내역은 유지됩니다.

## 3. 기능 명세

### 기능 명세

| ID | 기능 | 동작 규칙 | 수용 기준 (Given/When/Then) |
| --- | --- | --- | --- |
| F-01 | 시스템 관리자 최초 등록 및 로그인 | 시스템 관리자가 없을 때 이름과 동일한 숫자 4자리 비밀 확인값을 받아 생성합니다. 이미 있으면 새로 만들지 않고 로그인을 제공합니다. **반드시 서버 액션에서 Service Role 클라이언트를 사용하여 RLS(42501)를 방지**합니다. | **Given** 시스템 관리자가 0명이다. **When** 유효한 이름과 일치하는 숫자 4자리 비밀을 제출하여 서버 액션을 호출한다. **Then** 계정이 한 개 생성되고 로그인 상태가 된다. **Given** 관리자가 이미 있다. **When** 다른 사용자가 최초 등록을 시도한다. **Then** 두 번째 계정은 생성되지 않는다. |
| F-02 | 플라워샵 관리 | 시스템 관리자 인증 후 플라워샵을 등록하거나 기존 이름을 수정합니다. 서버 액션(Service Role)으로 처리하여 42501 에러를 방지합니다. | **Given** 시스템 관리자로 인증했다. **When** 유효한 플라워샵 이름을 저장한다. **Then** 메인 목록에 반영된다. **When** 같은 이름을 등록한다. **Then** 저장하지 않고 ‘이미 등록된 플라워샵 이름입니다.’를 표시한다. |
| F-03 | 플라워샵 검색 및 선택 | 검색어는 이름에 포함되는지 기준으로 찾고, 앞뒤 공백을 제거하며 대소문자 구분 없이 처리합니다. | **Given** 플라워샵이 등록되어 있다. **When** 검색어를 입력한다. **Then** 이름에 검색어가 포함된 항목만 보인다. **When** ‘선택’을 누른다. **Then** 해당 플라워샵의 `/shop/[id]`로 이동한다. 결과가 없으면 ‘검색 결과가 없습니다.’가 표시된다. |
| F-04 | 플라워샵별 관리자 등록·수정 | 관리자 조회·저장 때 현재 플라워샵의 `shop_id`를 반드시 사용합니다. 한 플라워샵에는 관리자 한 명만 둡니다. 서버 액션(Service Role)을 통해 저장하여 RLS 오류를 방지합니다. | **Given** 플라워샵에 관리자가 등록되어 있다. **When** 관리자 로그인 화면에서 본인 정보 수정 기능을 통해 새 이름이나 비밀을 입력한다. **Then** 해당 플라워샵 관리자 정보가 정상 수정된다. |
| F-05 | 직원 가입 신청 | 직원은 이름과 숫자 4자리 비밀 및 확인값으로 신청합니다. 신청 직후 상태는 `pending`이고 로그인은 허용하지 않습니다. 서버 액션(Service Role)을 통해 저장합니다. | **Given** 플라워샵을 선택했다. **When** 유효한 가입 정보를 제출한다. **Then** 해당 플라워샵에 `pending` 직원이 생성되고 완료 안내가 표시된다. 이름이 이미 사용 중이면 ‘이미 등록된 이름입니다.’를 표시하고 저장하지 않는다. |
| F-06 | 직원 승인·상태 관리·급여 조건 | 관리자는 신청자를 승인할 때 급여 유형(`hourly` 또는 `monthly`), 금액, 적용 시작일을 지정합니다. 직원은 `active`로 전환됩니다. 서버 액션(Service Role)으로 처리합니다. | **Given** 승인 대기 직원이 있다. **When** 관리자가 유효한 급여 조건을 설정하고 승인한다. **Then** 직원 상태가 `active`가 되고 급여 조건이 저장된다. **When** 관리자가 재직 직원을 퇴사 처리한다. **Then** 상태가 `resigned`가 되고 로그인 목록에서 제외된다. |
| F-07 | 직원 로그인 및 비밀 변경 | 로그인 목록은 선택한 플라워샵의 `active` 직원만 보여주며, **대표(관리자) 계정은 직원 로그인 목록에서 완전히 제외**합니다. 인증은 서버에서 해시를 비교합니다. | **Given** 한 플라워샵에 재직 직원과 대표 관리자가 있다. **When** 직원 로그인 목록을 연다. **Then** 재직 직원만 보이고 대표 관리자는 표시되지 않는다. |
| F-08 | 시급 직원 출퇴근 기록 | 시급 재직 직원은 날짜, 출근 시각, 퇴근 시각을 입력·수정합니다. 날짜 기본값은 오늘입니다. 서버 액션(Service Role)으로 저장하여 42501을 방지합니다. | **Given** 시급 재직 직원이 로그인했다. **When** 09:30~18:30을 저장한다. **Then** 540분으로 계산되어 보인다. **When** 퇴근 시각이 출근 시각과 같거나 빠르다. **Then** 저장하지 않고 ‘퇴근 시간은 출근 시간보다 늦어야 합니다.’를 표시한다. |
| F-09 | 직원의 월별 조회 | 직원은 월 선택으로 본인의 해당 월 근무 기록, 총 근무 시간, 예상 급여를 조회합니다. 월급 직원은 출퇴근 기록 없이 월 급여만 조회합니다. | **Given** 직원이 로그인했다. **When** 정산 월을 선택한다. **Then** 본인 데이터만 해당 월 기준으로 표시된다. 다른 직원 데이터는 응답에 포함되지 않는다. |
| F-10 | 관리자 월별 정산 및 기록 보완 | 관리자는 월을 선택하고 직원별 상태, 급여 유형, 총 근무 시간, 급여액을 확인합니다. 직원을 선택하면 하단 상세 내역이 보입니다. 서버 액션(Service Role)으로 저장합니다. | **Given** 관리자가 정산 월과 직원을 선택했다. **When** 상세를 확인한다. **Then** 해당 직원의 월 기록과 계산 내역이 표시된다. 월급 직원이면 출근·퇴근 항목이 없다. **When** 관리자가 유효한 시급 직원 근무 기록을 저장한다. **Then** 상세 내역과 합계가 갱신된다. |
| F-11 | 공통 배너 및 화면 문구 | 모든 화면 상단에 ‘플라워샵 근무 관리’를 표시합니다. 화면에 보이는 인증 라벨은 ‘비밀’, 확인 라벨은 ‘비밀 확인’입니다. | **Given** 사용자가 어떤 경로를 연다. **When** 화면이 표시된다. **Then** 공통 배너가 보이고, 사용자에게 표시되는 인증 문구에 ‘PIN’이 쓰이지 않는다. |
| F-12 | 입력 오류와 데이터 접근 제한 | 필수값 누락, 잘못된 날짜·금액·비밀, 권한 없는 요청은 서버에서 거부합니다. 42501 에러 방지를 위해 모든 쓰기 작업은 서버 전용 클라이언트를 통합니다. | **Given** 사용자가 다른 플라워샵의 직원·근무 기록을 요청한다. **When** 서버가 요청을 검증한다. **Then** 응답은 거부되고 다른 플라워샵 데이터가 반환되지 않는다. 잘못된 입력은 저장되지 않고 원인을 설명하는 안내가 표시된다. |

## 4. 화면과 주소(URL) 구성

### 공통 화면 규칙
- 모든 경로의 최상단에 세련된 ‘플라워샵 근무 관리’ 프로그램 배너를 표시합니다.
- 사용자가 보는 비밀 입력 라벨은 ‘비밀’, 확인 라벨은 ‘비밀 확인’으로 표시합니다. 입력은 숫자만 허용하고 최대 길이는 4자입니다. 화면의 오류·안내 문구는 한글로 표시합니다.
- 로그인 여부와 관계없이 페이지 틀은 표시합니다. 인증이 필요한 기능을 누르면 로그인 안내를 표시합니다. 잘못된 `shop_id`나 없는 플라워샵에는 ‘플라워샵을 찾을 수 없습니다.’를 표시합니다.

### 화면별 구성

| URL | 화면 및 상단부터의 구성 |
| --- | --- |
| `/` | 공통 배너 → 상단 배너 바로 아래 ‘플라워샵 관리’ 버튼 → 검색 입력(`플라워샵 이름을 검색하세요...`) → 별도 영역으로 지정된 ‘등록된 플라워샵’ 목록 카드 → 플라워샵 이름, 재직 직원 수, ‘선택’ 버튼. 결과가 없으면 ‘검색 결과가 없습니다.’ |

## 5. 데이터 모델

### 데이터베이스: Supabase PostgreSQL (전체 재생성 스크립트)
모든 비밀은 원문으로 저장하지 않고 서버에서 해시해 저장합니다. `pin_hash`는 4자리 비밀의 단방향 해시이며, 화면이나 API 응답에 포함하지 않습니다. 금액은 원 단위 정수입니다. 테이블을 모두 삭제한 상태이므로 아래 스크립트를 Supabase SQL Editor에 실행하여 테이블과 RLS를 완전히 새로 구축해야 합니다.

```sql
CREATE TABLE system_admins (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL,
  pin_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE shops (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 플라워샵마다 관리자 한 명
CREATE TABLE shop_admins (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  shop_id uuid NOT NULL UNIQUE REFERENCES shops(id) ON DELETE CASCADE,
  name text NOT NULL,
  pin_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE staff (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  shop_id uuid NOT NULL REFERENCES shops(id) ON DELETE CASCADE,
  name text NOT NULL,
  pin_hash text NOT NULL,
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'active', 'resigned')),
  created_at timestamptz NOT NULL DEFAULT now(),
  resigned_at timestamptz,
  UNIQUE (shop_id, name)
);

CREATE TABLE compensation (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  staff_id uuid NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
  pay_type text NOT NULL CHECK (pay_type IN ('hourly', 'monthly')),
  amount_krw integer NOT NULL CHECK (amount_krw > 0),
  effective_from date NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (staff_id, effective_from)
);

CREATE TABLE attendance (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  staff_id uuid NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
  work_date date NOT NULL,
  clock_in time NOT NULL,
  clock_out time NOT NULL,
  total_minutes integer NOT NULL CHECK (total_minutes > 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (staff_id, work_date),
  CHECK (clock_out > clock_in)
);

CREATE TABLE auth_attempts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  identity_hash text NOT NULL,
  attempted_at timestamptz NOT NULL DEFAULT now(),
  succeeded boolean NOT NULL DEFAULT false
);

-- RLS 활성화 및 정책 설정 (클라이언트 직접 접근 완전 차단)
ALTER TABLE system_admins ENABLE ROW LEVEL SECURITY;
ALTER TABLE shops ENABLE ROW LEVEL SECURITY;
ALTER TABLE shop_admins ENABLE ROW LEVEL SECURITY;
ALTER TABLE staff ENABLE ROW LEVEL SECURITY;
ALTER TABLE compensation ENABLE ROW LEVEL SECURITY;
ALTER TABLE attendance ENABLE ROW LEVEL SECURITY;
ALTER TABLE auth_attempts ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Deny direct access system_admins" ON system_admins FOR ALL USING (false);
CREATE POLICY "Deny direct access shops" ON shops FOR ALL USING (false);
CREATE POLICY "Deny direct access shop_admins" ON shop_admins FOR ALL USING (false);
CREATE POLICY "Deny direct access staff" ON staff FOR ALL USING (false);
CREATE POLICY "Deny direct access compensation" ON compensation FOR ALL USING (false);
CREATE POLICY "Deny direct access attendance" ON attendance FOR ALL USING (false);
CREATE POLICY "Deny direct access auth_attempts" ON auth_attempts FOR ALL USING (false);
```

### 중요: RLS 오류(42501) 방지 및 서버 액션 필수 규칙
- 모든 테이블에 `USING (false)` 정책이 적용되어 있으므로, 브라우저 클라이언트에서 직접 쓰기 작업을 수행하면 `42501` 오류가 발생합니다.
- **시스템 관리자 최초 등록**, 플라워샵 등록, 관리자/직원 가입 및 모든 데이터 변경 작업은 **반드시 Next.js Server Action 또는 Route Handler** 내부에서 `SUPABASE_SERVICE_ROLE_KEY`를 사용하는 전용 서버 클라이언트(`lib/supabase-server.ts`)를 통해 실행해야 합니다.

## 7. 기술 스택과 폴더 구조

### 기술 구성
- Next.js App Router와 TypeScript를 사용합니다. DB가 필요한 서버 기능은 Route Handler 또는 Server Action에서만 실행합니다.
- 화면 스타일은 Tailwind CSS로 구현합니다. 날짜 계산은 `date-fns`를 사용합니다.
- 데이터베이스는 Supabase PostgreSQL, 배포는 GitHub에서 Vercel 무료 플랜으로 합니다. 유료 외부 API는 사용하지 않습니다.
- 인증은 서버 검증 방식입니다. 성공한 로그인은 역할, 사용자 ID, 플라워샵 ID가 포함된 서명 쿠키로 유지합니다. 쿠키는 `HttpOnly`, `Secure`(운영 환경), `SameSite=Lax`로 설정합니다.

### 구현 경계 (42501 오류 원천 차단)
- 브라우저 클라이언트에서 `supabase.from('system_admins').insert(...)` 등을 직접 호출하면 RLS 정책 위반(`42501`)이 발생합니다.

## 8. 품질 기준 (성능·보안·접근성)

### 보안·정확성·접근성 기준
- 비밀은 정확히 숫자 4자리(`^[0-9]{4}$`)만 허용합니다. 확인 입력은 두 값이 정확히 일치해야 합니다. 원문 비밀은 DB, 로그, 오류 메시지, 응답에 남기지 않습니다.
- 시스템 관리자·플라워샵 관리자·직원 권한을 서버에서 매 요청 확인합니다. 직원은 본인 `staff_id`에 한해서만 기록을 조회·수정하고, 관리자는 본인 `shop_id` 데이터만 관리합니다.
- 플라워샵별 관리자 존재 확인과 등록은 현재 `shop_id`를 사용합니다. 관리자 한 명 제한은 DB의 고유 제약으로도 보장합니다.
- 로그인 실패는 계정 식별자별 15분 동안 5회까지 허용하고, 이후 15분 동안 차단합니다. 실패 사유는 ‘이름 또는 비밀을 확인해 주세요.’로 동일하게 표시합니다.
- 근무 기록은 직원·날짜당 하나입니다. 퇴근은 출근보다 늦어야 하고, 날짜를 넘기는 근무는 지원하지 않습니다. 근무 분은 출퇴근 시각 차이로 계산하며 휴게 시간을 빼지 않습니다.
- 적용 급여 조건은 근무 날짜 또는 급여 적용 날짜에 유효한 가장 최근 조건입니다. 시급 급여는 기록별 근무 분 기준, 월급은 달력 일수 기준으로 일할 계산합니다. 최종 합계는 원 단위 반올림합니다.
- 월급 직원은 근무 기록을 만들지 않습니다. 퇴사 직원의 과거 기록은 보존하지만 새 기록을 추가하지 못합니다.
- 모든 입력 필드는 키보드로 조작할 수 있고, 입력 라벨과 오류 문구를 화면 읽기 도구가 읽을 수 있도록 연결합니다. 버튼은 최소 높이 46px, 본문 기본 글자 크기는 16px입니다.
- 서버 오류가 발생하면 원문 SQL·키·스택 추적을 사용자에게 보여주지 않습니다. 저장 실패 시 입력 내용을 유지하고 재시도 안내를 표시합니다.

## 9. 배포와 운영

### 배포 절차
1. Supabase 대시보드의 SQL Editor에서 `supabase/migrations/0001_initial_schema.sql` 스크립트를 실행하여 모든 테이블과 RLS 정책을 새로 생성합니다.
2. GitHub 저장소의 `main` 브랜치를 Vercel 프로젝트에 연결하여 빌드·배포합니다.
3. Vercel 환경 변수에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `APP_SESSION_SECRET`을 올바르게 설정합니다. 서비스 롤 키와 세션 비밀은 서버 환경 변수로만 유지합니다.
4. 배포 완료 후 `meta.smokeRoutes`의 경로가 각각 HTTP 200을 반환하는지 확인합니다. 이 경로는 로그인이나 DB 데이터 없이도 페이지 틀을 렌더링해야 합니다.

### 기능 테스트 시나리오
1. **배너 및 메인 화면 구성** — **Given** 메인 화면 접속. **When** 화면을 렌더링한다. **Then** 상단 배너, 배너 바로 아래 ‘플라워샵 관리’ 버튼, 별도 영역으로 지정된 플라워샵 목록과 ‘선택’ 버튼이 올바르게 표시된다.
2. **시스템 관리자 최초 등록 (RLS 우회 검증)** — **Given** 시스템 관리자 0명. **When** 이름과 숫자 4자리 ‘비밀’을 제출하여 서버 액션을 호출한다. **Then** 오류 없이 관리자가 생성되고 로그인된다.
3. **플라워샵별 관리자 독립성 및 본인 수정** — **Given** 플라워샵 A에는 관리자가 있고 B에는 없다. **When** 관리자 로그인 화면에서 본인 정보 수정 기능을 사용한다. **Then** 해당 관리자 정보가 안전하게 수정된다.
4. **직원 가입 및 승인 (대표 제외)** — **Given** 직원이 가입을 신청한다. **When** 관리자가 급여 유형과 금액, 적용 시작일을 설정하여 승인한다. **Then** 직원 상태가 `active`로 변경되고 로그인할 수 있으며, 대표 관리자는 직원 로그인 목록에 나타나지 않는다.
5. **시급 및 월급 정산** — **Given** 시급 또는 월급 직원. **When** 관리자가 정산 월을 선택하고 직원을 선택한다. **Then** 시급 직원은 출퇴근 및 근무 시간 내역이 보이고, 월급 직원은 일할 계산된 급여가 표시되며 출퇴근 항목은 제외된다.
6. **문구 검증** — **Given** 모든 인증 및 화면 요소를 확인한다. **Then** ‘PIN’ 단어 대신 ‘비밀’ 문구가 사용되었음을 확인한다.
